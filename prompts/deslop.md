---
description: Remove AI-typical phrasing, comments, and compatibility layers from prose or code
argument-hint: "<file-or-dir>"
---
Rewrite ${@:-the file or directory under discussion; if none is clear, ask which path} so
it no longer reads as model output. Search for the habits below. English and Korean lists
both apply. Keep technical content, math, labels, defined terms, identifiers that still
name the live path, and the strength of every claim. Do not invent facts, numbers,
sources, opinions, or first-person color the text did not already have. Do not swap AI
filler for punchy filler. If a span is fluent but empty, cut the empty frame or leave it;
do not fabricate a sharper claim.

If the argument is a directory, walk source and prose files. Skip generated output,
lockfiles, and vendored trees. Prose files get the English and Korean lists. Code files
get the code pass first, then the lists on remaining comments, docstrings, and
user-visible strings.

Phrase swaps alone are not enough. Structure and rhythm are the stronger tells: binary
contrasts, forced threes, metronomic sentence length, punchline fragments, restated
headings, and paragraphs that land on a slogan. Edit clusters of habits, not isolated
words. When several habits sit in one sentence, rewrite that sentence once.

Remove all figurative language: metaphor, simile, and personification, in any language.
Every replacement states the literal operation. Never introduce figurative language or
an em dash in a replacement.

Work in passes, then write the files.

Code pass, before prose. Prefer deleting residue over rewriting algorithms. Match the
surrounding file. Do not reformat, rename, or touch unrelated files. Do not add packages, flags, or tests. Do not skip or weaken a test to make a change look
green. Delete excessive tests as residue, not as a way to hide a regression.

One live path. Delete compatibility layers, fallbacks, unused flags, shims, and wrappers
that only preserve an old name. Remove the obsolete path in the same change. Rename
identifiers that became wrong (`*_v2`, `newX`, `legacyX` when only X remains). Do not add
a replacement abstraction. Do not change the remaining path's behavior. If a second path
might still be live, leave it and report it.

Then delete comments that do not encode a constraint, and the leftover constructs below.

Pass 1, structure: contrast frames, tricolons, fragments, repeated openings, synonym
cycling, heading restatements, section-end recaps, mechanical transitions, copula
dodges, -ing analyses, false ranges, vague sources, hollow closings.
Pass 2, diction: filler, inflation, marketing adjectives, AI vocabulary, Korean
translationese, punctuation tics.
On code, pass 1 and 2 touch only comments, docstrings, and user-visible strings.
Then re-read the changed regions. Ask: what still sounds generated? Did any claim,
name, number, citation, LaTeX token, or live-path behavior change? Treat either as an
error and fix it.

Code comments to delete:
- Restate the next line or the signature (`// Import React`, `// Return the value`).
- Narrative JSDoc or XML-doc that only repeats the member name.
- Change history and past behavior: "Added for", "FIXED", "now correctly",
  "previously", "used to", "formerly", "no longer", "replaces the old",
  "instead of the previous". Describe the current constraint, or delete the comment.
- Contrast with another implementation or with deleted code.
- Agent process notes: phases, "generated by", "the model", "for the agent".
- Correctness emphasis: "This ensures", "Important:", "Make sure to".
- Section banners: `// ===== Helpers =====`.
- Chatbot leftovers, emoji, "Note that", "It's worth noting".
- Untracked TODO/FIXME/HACK with no issue link. Keep a TODO that cites a tracker.
Keep a comment only when it states a non-obvious constraint or a checkable reference
(theorem, definition, algorithm, RFC, file). Example to keep:
`z1 = (P11 + P01 + P10) - s. Subtract s so z1 does not carry the secret (PINI, Def 5).`
Example to delete: `The FIXED kernel now satisfies Def 5 directly.`

Docs and comments describe the current behavior only. Delete narration of what used to
happen, what was replaced, or why the old path existed. Keep past tense only in a
changelog, release note, or migration guide. Rewrite "This function was added to replace
the previous O(n^2) scan" to the current cost, or delete it. Korean: "이전에는",
"기존에는", "예전에는", "바뀌었습니다", "더 이상 ~하지 않습니다" in ordinary docs
and comments, same rule.

Compatibility layers and fake resilience to delete:
- Two implementations of one behavior selected by a flag, env var, or `legacy`/`compat`
  name.
- Deprecated wrappers that only forward arguments unchanged.
- Fallback branches, default-on polyfills, and unused options kept "just in case".
- Feature flags whose both sides are never taken, or whose one side is the only live
  path.
- Hidden fallbacks that turn missing input, failed diagnostics, or impossible states
  into a success-looking default without surfacing the failure.
- Extra defensive checks or try/catch on a trusted, already-validated path.
- Catch that is empty, only logs, or rethrows the same error with no context.
- `if (true)` / `if (false)`, unreachable code after return/throw, empty function bodies.
After deletion, remove now-dead imports, types, tests that only covered the old path,
and comments that described it. Do not leave a stub.

Other leftover constructs to delete or collapse:
- Thin helpers that exist only because the agent did not call the existing function.
- Duplicate copies of a formatter, guard, or type already in the tree. Keep one.
- Debug leftovers: `console.log`/`debug`/`info`, `print(...)` in library modules.
- Type theater: `as any`, `as unknown as T`, `@ts-ignore` without a reason, re-coercing
  an already-typed primitive with `String`/`Number`/`Boolean`.
- Generated names `helper_1`, `data2`, `temp1`. Rename to the domain noun already in
  that function. Leave ordinary short names (`i`, `err`) alone.
- Tautological tests that recompute the implementation and compare it to itself.

Excessive tests to delete:
- Cases that only rename inputs or restates another case in the same file.
- Speculative cases for states the type, constructor, or validator already excludes.
- Tests of private helpers, getters, or mappers that have no public contract.
- Snapshots that freeze an entire tree so CI stays green. Keep a narrow assertion of
  the behavior.
- Tests that assert a mock was called instead of an observable result.
- Tests whose only job was the deleted compat/fallback path.
- Files or `describe` blocks added for a one-line wrapper that should not exist.
- Tests whose claim is that something does not happen: `not.toHaveBeenCalled`,
  `not.toThrow`, `not.toContain`, "should not X", "does not Y". Absence is not a
  contract. Delete them. Assert the value, state, or call that must occur.
Keep a test that asserts an independently known outcome at a public boundary. If it is
unclear whether a test is residue, leave it.

English habits to remove:

- Contrastive scaffolding: "not X, but Y", "It is not that ... rather ...", "less about
  X than Y", "The point is not X. The point is Y.", "What is needed is X", "Not because
  X. Because Y.", "X isn't the problem. Y is." Assert the positive claim. Drop the
  negation runway.
- Negative listing: "Not A. Not B. C." State C.
- Forced groups of three: "X, Y, and Z" as cadence; "simple yet powerful"; stacked
  tricolons. Keep two items, or one specific item. Keep a real three-item inventory.
- Dramatic fragments and punchline endings: "X. That's it.", a row of three-word
  sentences, a paragraph that closes on a slogan. Write a complete sentence. Vary how
  paragraphs end.
- Copula dodge: "serves as", "stands as", "marks a", "boasts", "features" where "is" or
  "has" is enough.
- Superficial -ing analyses tacked on a fact: "highlighting", "underscoring",
  "ensuring", "reflecting", "showcasing", "contributing to". Cut the participle or
  replace it with a specific claim already in the text.
- False ranges: "from X to Y" when X and Y are not a scale. List the items.
- Repeated openings and synonym cycling: several sentences starting with the same
  subject; renaming one thing ("users" / "customers" / "clients") inside a paragraph.
  Merge or keep one name.
- Generic openings and meta-structure: "In today's ... world", "As we navigate",
  "Have you ever wondered", "Imagine a world where", "In this section, we'll",
  "As mentioned earlier". Start with the claim. Delete the tour of the document.
- Throat-clearing and fake candor: "Here's the thing", "Look,", "Let's dive in", "Let's
  unpack", "Here's what you need to know", "The real question is", "at its core",
  "Honestly?". Delete the announcement; keep the fact.
- Heading restated in the next sentence; section-end recap of the heading; "In
  conclusion" / "Overall" / "In summary"; generic optimism ("the future looks bright",
  "exciting times"). Cut the recap. End on the last concrete fact.
- Mechanical transitions used as paragraph glue: "Furthermore", "Moreover",
  "Additionally", "That said", "With that in mind", "Having established that". Start
  with the next fact.
- Inflated importance: "stands as a testament", "pivotal moment", "evolving landscape",
  "indelible mark", "key turning point", "setting the stage for". Keep the dated fact.
- Vague sources and vague declaratives: "Experts argue", "Observers have cited",
  "Industry reports", "The implications are significant", "The reasons are structural".
  Name the source already in the text, or drop the frame and keep the specific claim.
- Significance inflation: "Crucially", "Importantly", "Notably", "Remarkably", "The key
  insight is", "is worth stating/noting", "subtle but important", "This is precisely
  where", "It is no accident that". Delete the frame and keep the fact.
- Uniqueness emphasis: "The only X is Y", "the sole", "one and only", "exactly one" used
  for weight rather than a counted fact. Write "X is Y" or "X: Y".
- Settlement verbs outside actual conclusions: "This confirms", "This establishes",
  "This settles", "This cements", "locks in". State the fact; reserve conclusion verbs
  for theorem conclusions.
- Restatement tics: "In other words", "Put differently", "The upshot is", "That is,"
  followed by a paraphrase of the previous sentence. Keep the better version, delete
  the other.
- Colon drama and rhetorical setup: "The reason is simple: ...", "One fact does the
  work: ...", "Why does this hold? Because ...", "The result? ...". Convert to a plain
  declarative sentence.
- Answering an objection nobody raised: "This isn't about", "I'm not saying", "Don't
  get me wrong", "Some might say". State the real constraint. Rejecting a fake
  alternative ("A tempting approach would be") the same way: delete the unused option.
- "Whether you're X or Y" false inclusivity. Address the actual audience.
- Formulaic sayings: "X is the Y of Z", "X is not a tool but a mirror". Replace with
  the specific claim.
- Motivational endings and enablement rhetoric: "This will enable", "This unlocks",
  "This paves the way", "This empowers", "This lays the foundation". State the measured
  change or the next concrete operation.
- Borrowed-domain metaphors. Replace with the literal property. Keep a word only when it
  is a defined term or a real object in the text.
  Construction: "load-bearing", "seams", "scaffolding", "foundation", "bridge",
  "architecture", "ladder", "footgun", "sharp edges", "escape hatch", "guardrails",
  "moving parts", "surface area", "blast radius", "happy path", "north star".
  Electrical: "wiring", "gate", "circuit", "signal", "current", "voltage",
  "short-circuit", "fuse", "under the hood", "heavy lifting", "unlocks" as a verb.
  Fluid: "pipeline" outside hardware, "flow" outside dataflow, "stream" outside a stream
  type, "tap", "drain", "leak" outside a leakage definition.
  Space: "realm", "landscape", "tapestry", "in the world of", "field" as atmosphere,
  "domain" outside a formal domain.
  Journey: "path" as progress, "roadmap", "journey", "navigate", "move forward",
  "walk through", "step" as a narrative beat.
  War: "battle", "fight", "combat", "attack" outside security, "weaponize", "shield",
  "campaign".
  Biology: "skeleton", "backbone", "heartbeat", "DNA", "organ", "limb".
  Personification: code that "wants", a system that "thinks", an algorithm that "learns"
  outside ML, data that "says", values that "live"/"survive"/"die"/"meet"/"see"/
  "remember", proofs that "do the work" or "rest on" something, components called
  "twins" or "cousins".
  Replacements: persists, remains, is stored, is combined, depends on, variant,
  counterpart; essential, central, boundary, risk, error-prone case, override, default
  case; interface, join, edge; "increases X by Y" / "replaces A with B"; because, due to.
- Hedging and throat-clearing frames: "It's worth noting", "It is important to note",
  "Note that", "Notably", "Interestingly", "Arguably". Delete the frame.
- Filler intensifiers and pet adjectives: "essentially", "effectively", "fundamentally",
  "at its core", "simply", "just", "clean", "elegant", "principled", "robust",
  "powerful", "seamless", "cutting-edge", "best-in-class", "delve", "landscape" as an
  abstract noun, "underscore" as a verb, "testament", "vibrant", "fostering",
  "leverage", "harness", "showcase", "pivotal", "crucial", "nuanced",
  "groundbreaking", "game-changer", "transformative". Delete, or replace with a
  checkable property already in the text.
- Punctuation and format habits: em dashes, en dashes used as dashes, exclamation
  marks, rhetorical questions, triadic "X, Y, and Z" rhythm added for cadence, bold
  mini-headings on every bullet ("**Performance:** ..."), title case in headings,
  decorative emoji, chatbot leftovers ("I hope this helps", "Would you like...").
- Metronomic rhythm: four or more consecutive sentences of similar length. Break one.
  Do not manufacture staccato to compensate.

Korean habits to remove:

- Calques of English metaphors: "배선" for connections outside literal circuit wiring,
  "게이트", "파이프라인을 타고", "레버리지", "훅", "로드맵", "여정", "지형",
  "풍경", "뼈대", "심장부", "전투", "방패". Describe the actual relation: 연결,
  호출 순서, 의존, 순서, 구조, 중심.
- Coined word-for-word translations of English compound terms: "wiring family" →
  "배선족", "glue code" → "접착 코드". Such words do not exist in Korean technical
  usage. Use the established Korean term when one exists; otherwise keep the English
  term in English.
- Settlement verbs outside actual conclusions: "확정했습니다", "확정됩니다", "확립합니다",
  "못박습니다", overused "보장합니다". Use the plain verb for what happened: 정해집니다,
  저장합니다, 기록합니다.
- Contrast and inflation calques: "단순히 X가 아니라 Y입니다", "중요한 것은 X가 아니라
  Y라는 점입니다", "핵심은 ~라는 점입니다", "주목할 점은", "흥미롭게도", "결정적으로",
  "솔직히 말하면", "사실은". Assert the claim directly.
- Personification and restatement: 값이 "살아남습니다"/"살아있습니다" → "유지됩니다";
  "다시 말해"/"즉," followed by a paraphrase of the previous sentence → keep one version.
- Translationese endings and connectives: overused "~하게 됩니다", "~인 셈입니다", "~라고
  할 수 있습니다", and "~를 통해" where "~로" or a direct verb suffices. Also: "~에
  대하여/관하여" → object + 을/를; "~하기 위하여" → -려고/-도록; "~을 가지다" → "~이
  있다"; "~로부터" → "~에서"; "~에 있어" → "~에서".
- Signpost stacking: 또한, 이를 통해, 더 나아가, 결과적으로, 전반적으로, 한편,
  뿐만 아니라 used as paragraph glue. Start with the next fact.
- Heading warm-ups and recaps: "살펴보겠습니다", "알아보겠습니다", "다음과 같습니다",
  "정리하면", "앞으로의 행보가 기대됩니다". Cut. Keep the last concrete fact.
- Uniform 합니다 / 할 수 있습니다 cadence; slogan runs ("빠릅니다. 간단합니다.
  강력합니다."). Vary sentence length. Keep the document's register; do not mix
  합니다/해요/-다 unless the source already does.
- English comma habits in Korean: comma after 최근/특히/그러나/물론; comma after
  connective endings (-고, -어서, -지만, -며); "A, B, 그리고 C". Drop those commas or
  join with 와/과, 이나/거나.
- Vague authority and praise without evidence: "많은 전문가들은", "업계에서는", "여러
  연구에 따르면", "혁신적인", "최적화된", "강력한", "핵심적인", "획기적인". Keep the
  named source or the measured property; drop the frame.
- Synonym cycling of the same actor: 사용자 / 고객 / 이용자 / 클라이언트 in one
  paragraph. Keep one term.
- Nominalization and availability chains: -화/-성/-적, "것/부분/측면", "제공됩니다",
  "진행됩니다", "가능합니다" repeating. Name the actor and the verb when the source
  already has them.
- Overused Sino-Korean fillers when a plain verb exists: 진행하다/실시하다 → 하다;
  활용하다 → 쓰다/사용하다; 도출하다 → 얻다; 존재하다 → 있다; 위치하다 → 있다. Keep
  a domain term that is already the document's vocabulary.
- Unnecessary plural 들 after 많은/여러/모든.

Examples of the direction of change:

- "is worth stating separately because" → "is stated separately because"
- "the hold survives because no intervening nwrite mentioned 1"
  → "the hold persists because no intervening nwrite mentioned 1"
- "walks the whole ResNet-20 through the same lens"
  → "applies the same construction to ResNet-20"
- "the sentence the surrounding claims rest on"
  → "the claim the surrounding results depend on"
- "the two shares of a value never meet inside the node"
  → "the two shares of a value are never combined inside the node"
- "their *_step_secret twins" → "their *_step_secret counterparts"
- "It's not about latency. It's about tail latency under load."
  → "The constraint is tail latency under load."
- "Gallery 825 serves as the exhibition space" → "Gallery 825 is the exhibition space"
- "In today's fast-paced world, caching is crucial, highlighting its pivotal role"
  → "Caching reduces repeated queries."
- "The pipeline is simple, robust, and seamless" → "The pipeline has two stages."
- "이 값은 다음 단계까지 살아남습니다" → "이 값은 다음 단계까지 유지됩니다"
- "슬롯 배치를 확정했습니다" → "슬롯 배치를 정했습니다"
- "모듈 간 배선을 따라" → "모듈 간 호출 순서를 따라"
- "핵심은 속도가 아니라 정확도라는 점입니다" → "제약 조건은 정확도입니다"
- "설정을 살펴보겠습니다. 알림을 끄려면" → "알림을 끄려면"

Keep the document's own terminology even when it looks figurative: if "gate", "wire",
"probe", "handoff", "leakage", "배선" (in a literal circuit or PCB context), or similar
words are defined terms of the text, they stay.
Only remove figurative language that is not part of the document's vocabulary.
Do not treat one em dash, one "however", polish, or academic diction as proof by itself.

Prose files: do not reflow paragraphs, reword math, or touch LaTeX commands, labels,
\ref/\cite, code fences, YAML, or document structure. Do not add contractions to
academic prose. Do not add "you" or personality to technical or formal text.
Code files: do not reformat unrelated lines. Do not rewrite algorithms for style. Do not
add tests, compatibility shims, or feature flags. After a deletion, confirm the remaining
path still compiles at the call sites you touched.
When in doubt whether a phrase is an AI habit, or whether a code path is dead, leave it.
Apply the edits to the files, then re-read the changed regions to confirm no markup
broke.
